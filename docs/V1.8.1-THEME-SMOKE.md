# v1.8.1 preliminary theme browser smoke

On 2026-11-12 (Asia/Shanghai), an isolated disposable Panel loaded all 64
hash-verified original archives from the 2026-11-08 locked market catalog.
The scan opened the public root at 1280×900 and 390×900, waited 1.2 seconds,
and recorded response status, body text length, page exceptions and console
errors. No production Panel was changed. The complete per-theme archive hash,
version and results are in [the redacted summary matrix](./V1.8.1-THEME-MATRIX.md);
the temporary Panel binary SHA-256 is recorded in the retained local report. The fixture used the
working-tree source built before final release CI and the built-in theme archive.

All 128 public-root requests returned HTTP 200 with nonempty body text. Two
views of the original `komari-next-pro` archive raised React hydration error
#418. Fifteen theme archives emitted console errors in both viewports, including
rate limiting, missing resources, and external-service CORS failures. Some
errors may be fixture or network dependent; they are retained rather than
classified as product defects without further investigation. The original
archives were tested without local patches. External requests were not blocked
in this first run; the test host address in the saved console text is redacted.

This is **not** a pass for the 64-theme gate. The initial scan did not exercise
every theme's mobile controls or authenticated routes, verify hydration beyond
observed exceptions, or test patched variants. The scanner is available at
`deploy/calibrate/theme_smoke.py`; it now blocks external requests in future
runs so untrusted themes cannot contact third parties from the test host.

## Next Pro static-server control

On 2026-11-15, the locked original Next Pro archive (SHA-256
`e557a5fe89eab5ec0b553f631511e499a01b611481e13771e8c5d3f8268b50ba`)
was extracted into a temporary directory and its `dist` served directly by
Python's static HTTP server, with no Nekomari Panel. Chromium loaded the root
at 1280×900 and 390×900 with external requests blocked. Both returned HTTP
200 and reproduced React hydration error #418. This rules out the Panel being
required to trigger this particular exception. The static server does not
provide Panel APIs, so it does not identify the underlying mismatch or prove
that every production occurrence has the same cause. The original archive
still fails the recorded browser gate; a locally patched archive is not a
replacement for the locked market archive.

### Original archive footer mismatch investigation

On 2026-11-15, a diagnostic interception of the original React bundle logged
the element at the hydration exception on the standalone static server. The
client expected a `p` containing `Komari-Next and LIU`; the corresponding
server HTML contained a `div` with the same text and a GitHub attribution
link. This identifies one concrete mismatch in the shipped archive, without
establishing that it is the only cause in other conditions.

In temporary copies, removing the three `data-k` scripts alone, or changing
the server footer alone, still yielded #418 at both viewports. Combining the
footer change with removal of all three `data-k` scripts produced no observed
page exception in this static-server check. The footer-only copy still had
the `div` at hydration time, despite its modified initial HTML. Separately
removing the two extra external scripts or the expiry script did not have
the same effect in these controls. These are diagnostic changes, not a
proposed distributable patch: removing the `data-k` scripts also removes an
integrity check, and the footer experiment removes an attribution link.
The original archive, production installation, and release gate remain
unchanged. This test does not cover API-dependent hydration, all interactions,
or late script behavior.

## Home-page HEAD requests

An additional diagnostic scan loaded all 64 original archives at both
viewports. All 128 roots returned 200 and nonempty text; Mochi and Next Pro
were again the only archives with page exceptions. The scan captured failed
requests but did not exercise all interactions. Two themes, `komari-deer` and
Next Pro, sent `HEAD /`, which the Panel returned as 404. A focused repeat
captured the method and response; the earlier attribution of Next Pro's 404
to an RSC prefetch was not established by that check.

The candidate now answers `HEAD /` with the public shell's headers and no
body, retaining conditional ETag behavior. In a disposable Panel built with
that change (SHA-256
`8e55d782d8027861353ad5c0e68c4ac33b8babf0636d1a4c7addb2b1f9328a5f`),
the two original themes no longer observed that local 404 at either viewport.
The browser still reported an aborted HEAD request on context teardown; Next
Pro still raised #418. This check does not close the theme gate. Detailed
diagnostics are retained at `/tmp/nekomari-v181-all-request-diagnostics.json`
and `/tmp/nekomari-v181-head-check.json` on the test host.

### Footer timing control

A further standalone diagnostic retained all three original `data-k` scripts
and their attribution link. In a temporary copy, it replaced the static footer
with the `p` expected by the client and deferred the footer-rewriting `f1a3`
script. At both desktop and mobile sizes, a 100 ms delay still produced #418;
500 ms and 1500 ms produced no observed exception over an 11-second observation,
and the attribution link and three scripts remained present. These were one
observation per combination, with external requests blocked.

The 1500 ms version was then tested under emulated 500 ms network latency and
62,500 bytes/second throughput: #418 returned at both sizes despite retaining
the attribution link and scripts. Thus a fixed delay is not a reliable fix for
the hydration race. This was a static-server control, not a distributable theme
patch or a full Panel and interaction test. The original market archive remains
unchanged and the gate remains open.

## Synthetic-node public-root scan

On 2026-11-15, a disposable Panel using the HEAD-fix candidate binary
(SHA-256 `8e55d782d8027861353ad5c0e68c4ac33b8babf0636d1a4c7addb2b1f9328a5f`)
created a synthetic node and accepted one `agent.report` containing CPU,
memory, disk and network fields. The 64 hash-verified original archives were
then selected one at a time and their public root loaded at 1280×900 and
390×900, with external requests blocked. After 1.5 seconds all 128 responses
were HTTP 200 and nonempty. In 122 views the full synthetic node name occurred
in the DOM. Mochi showed the name but raised `Failed to fetch` at both sizes,
consistent with the blocked map request described above. Original Next Pro
raised #418 in both views and the exact name was absent; `komarihome` and
`nezha-BITJEBE` also lacked the exact name at both sizes without page errors.

A separate 10-second check of those three originals showed Next Pro's node name
truncated by the theme, while its CPU and network fields were displayed; #418
still occurred. `nezha-BITJEBE` displayed the full node name after the longer
wait. `komarihome`'s root is a homepage with a monitoring navigation item, and
did not show the node there. These follow-ups explain why the original
exact-name observation cannot by itself be treated as a product failure; they
do not establish correctness of the themes' data or other routes. This scan
used an earlier candidate Panel, a single synthetic report, a short fixed wait,
and no data-bearing route or interaction assertions. It is not the full 64
browser/hydration/mobile acceptance gate. Detailed local results are retained
in `/tmp/nekomari-v181-data-theme-scan.json` and
`/tmp/nekomari-v181-data-theme-detail.json`; the disposable Panel was removed.
