# v1.8.1 preliminary theme browser smoke

On 2026-11-12 (Asia/Shanghai), an isolated disposable Panel loaded all 64
hash-verified original archives from the 2026-11-08 locked market catalog.
The scan opened the public root at 1280×900 and 390×900, waited 1.2 seconds,
and recorded response status, body text length, page exceptions and console
errors. No production Panel was changed. The complete per-theme archive hash,
version and results are in [the redacted summary matrix](./V1.8.1-THEME-MATRIX.md);
the temporary Panel binary SHA-256 is recorded in the retained local report. The fixture used the
working-tree source built before final release CI and the built-in theme archive.

All 128 public-root requests returned HTTP 200 with nonempty body text. Two
views of the original `komari-next-pro` archive raised React hydration error
#418. Fifteen theme archives emitted console errors in both viewports, including
rate limiting, missing resources, and external-service CORS failures. Some
errors may be fixture or network dependent; they are retained rather than
classified as product defects without further investigation. The original
archives were tested without local patches. External requests were not blocked
in this first run; the test host address in the saved console text is redacted.

This is **not** a pass for the 64-theme gate. The initial scan did not exercise
every theme's mobile controls or authenticated routes, verify hydration beyond
observed exceptions, or test patched variants. The scanner is available at
`deploy/calibrate/theme_smoke.py`; it now blocks external requests in future
runs so untrusted themes cannot contact third parties from the test host.

### Original archive footer mismatch investigation

On 2026-11-15, a diagnostic interception of the original React bundle logged
the element at the hydration exception on the standalone static server. The
client expected a `p` containing `Komari-Next and LIU`; the corresponding
server HTML contained a `div` with the same text and a GitHub attribution
link. This identifies one concrete mismatch in the shipped archive, without
establishing that it is the only cause in other conditions.

In temporary copies, removing the three `data-k` scripts alone, or changing
the server footer alone, still yielded #418 at both viewports. Combining the
footer change with removal of all three `data-k` scripts produced no observed
page exception in this static-server check. The footer-only copy still had
the `div` at hydration time, despite its modified initial HTML. Separately
removing the two extra external scripts or the expiry script did not have
the same effect in these controls. These are diagnostic changes, not a
proposed distributable patch: removing the `data-k` scripts also removes an
integrity check, and the footer experiment removes an attribution link.
The original archive, production installation, and release gate remain
unchanged. This test does not cover API-dependent hydration, all interactions,
or late script behavior.
