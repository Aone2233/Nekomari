# v1.8.1 preliminary isolated netem evidence

## Later local loopback failure

On 2026-11-15, an Agent suite on the Linux x86-64 development host failed
`TestICMPLoopbackCalibration`: Agent median 126 µs versus system `ping`
average 65 µs, difference 61 µs against the 50 µs threshold. The two groups
run sequentially and use different summary statistics; this observation does
not identify the cause. It is not erased by the separately scoped LAN and
netem successes below. The subsequent same-probe comparison is recorded
below. The raw local test output is retained in the command transcript rather
than committed.

### Same-probe loopback packet comparison

Later that day, a predeclared experiment on the same Linux x86-64 host ran
three consecutive groups of 30 `icmpPing` probes to loopback. `tcpdump`
captured the corresponding request/reply pairs on `lo`, matched by ICMP ID,
sequence and send order; each group captured 60 packets and reported zero
kernel drops. The predeclared per-probe Agent/capture difference was at most
50 µs. All 90 samples exceeded it:

| Run | Matched probes | Median absolute difference (µs) | p95 (µs) | Maximum (µs) | Over 50 µs |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 30 | 138.5 | 232 | 272 | 30 |
| 2 | 30 | 133.5 | 212 | 219 | 30 |
| 3 | 30 | 150.5 | 256 | 350 | 30 |

The test executable SHA-256 was
`c0ec12431ce70e216a3328f120826cc15d86aebdaea233f20d041a9ceafc8a13`;
its ICMP implementation matches the candidate's function text byte for byte.
The raw captures, logs and predeclared protocol remain in
`/tmp/nekomari-v181-loopback-paired`; none is committed. Captures use the
interface's software timestamps and do not independently measure the Agent's
user-space send/receive boundaries.

Inspection of `pro-bing` v0.7.0 shows that it inserts a timestamp before
marshalling and sending, then takes the receive time in `processPacket`
after socket read and channel delivery. Thus its interval includes work and
scheduling outside the captured on-interface interval. That is consistent
with the observed excess, but this experiment does not isolate the size of
each contributor or prove that capture timestamps equal wire time. The 50 µs
same-probe target fails on this host and remains open; the physical LAN
checks below used a separate 1 ms bound.

### Receive-timestamp prototype

A separate Linux-only prototype measured from a user-space send timestamp to
`SO_TIMESTAMPNS` kernel receive time, using an ICMP socket with random echo
payloads; it was not installed in the Agent. Three predeclared groups of 30
for each socket type were compared against matching loopback packet captures,
with the same 50 µs per-packet bound and no discarded runs or capture drops:

| Socket | Run | Median difference (µs) | p95 (µs) | Maximum (µs) | Over 50 µs |

| Raw | 2 | 49.5 | 61 | 74 | 11 |
| Raw | 3 | 47.0 | 67 | 70 | 3 |
| Unprivileged ping | 1 | 61.0 | 78 | 80 | 28 |
| Unprivileged ping | 2 | 59.0 | 76 | 76 | 30 |
| Unprivileged ping | 3 | 61.5 | 71 | 117 | 28 |

The prototype source and binary SHA-256 were respectively
`cc9c98769e7eee94b93d5e39e334db40987c6ea4ef7bd8bfc693d04baa29bc39` and
`c30afbd7f52d312c50c8d0f9a14ba966cb525c93e5cda711b168b316ee574fd7`.
Protocol, logs and captures are under
`/tmp/nekomari-v181-icmp-kernel-prototype`; the prototype is
`/tmp/nekomari-icmp-kernel-prototype.go`. It reduces receive-side scheduling
overhead but still includes user-space send and socket work and uses realtime
timestamps. It fails the predeclared bound, does not test IPv6, clock steps,
timeouts, permission fallback or non-Linux systems, and is not a production
fix. A separate send-timestamp investigation remains open.

## Predeclared isolated repeat

On the same date a fresh temporary namespace and veth were used for a new
experiment. Before running, the protocol fixed three runs of 120 production
`icmpPing` calls for each of 0%, 1%, 5%, and 20% netem egress loss, with no
retries or discarded runs. A `tc` egress action counted echo requests before
netem; tcpdump on the source veth counted replies. Each run required 120
counted sends, exact agreement between captured replies and Agent successes,
zero capture kernel drops, and inclusion of the configured loss probability
in a two-sided nominal 99.9% Wilson interval. The 0% run additionally
required zero observed loss. The wide intervals make this a coarse consistency
check; Wilson coverage is approximate, especially at boundaries.

| Netem loss | Agent successes / captured replies, three runs | Observed loss intervals (nominal 99.9%) |
| --- | --- | --- |
| 0% | 120 / 120 / 120 | 0–8.28% each |
| 1% | 120 / 118 / 117 | 0–8.28%, 0.23–11.10%, 0.46–12.40% |
| 5% | 113 / 115 / 116 | 1.82–17.16%, 1.07–14.85%, 0.75–13.64% |
| 20% | 93 / 95 / 93 | 12.55–37.00%, 11.32–35.18%, 12.55–37.00% |

All twelve runs met the predeclared checks, including 120 independently
counted sends and zero capture drops in each run. Protocol, counters, logs and
captures remain on the test host in `/tmp/nekomari-v181-netem-predeclared`;
the disposable network was removed. This improves the loss evidence, but it
does not verify a physical LAN or close the LAN latency acceptance gate.

## OC424 cloud-subnet ICMP comparison

On 2026-11-13 (Asia/Shanghai), a candidate `71c4d7b` Agent measurement test
binary ran on OC424 against its responding default gateway. A preliminary
30-probe run passed. Before the repeat, the protocol fixed three runs, each
with 30 sequential calls to the actual Agent `icmpPing` path and 30 system
`ping` probes, with source-interface capture. Each run required all replies,
zero capture drops, per-packet Agent/capture RTT differences at most 1 ms,
and an Agent/system-ping median difference at most 1 ms. All three passed.

| Run | Agent and ping replies | Agent median | ping median | Maximum per-packet difference |
| --- | --- | ---: | ---: | ---: |
| 1 | 30/30 each | 0.298 ms | 0.228 ms | 0.146 ms |
| 2 | 30/30 each | 0.342 ms | 0.205 ms | 0.155 ms |
| 3 | 30/30 each | 0.322 ms | 0.202 ms | 0.264 ms |

Across the 90 Agent probes, the absolute Agent/capture difference had median
0.121 ms and p95 0.145 ms. Raw captures and logs remain on OC424 under
`/tmp/nekomari-v181-lan-repeat-urrBMd`; the test binary SHA-256 is
`12225738019a386d65c6c450159df193ec028353273d8fe8807720a01d83d6c5`.
The target is on OC424's cloud subnet, but its physical topology is unknown;
the observation is not proof of a physical LAN path. No production interface
was altered.

## MAC-WAN physical LAN ICMP comparison

On 2026-11-15, MAC-WAN measured its physical JDCloud AX6600 router over its
wired LAN. A candidate Agent test binary invoked the production `icmpPing`
path in a disposable host-networked container with raw-socket permission;
tcpdump captured matching packets on the source interface. System `ping` ran
on the host. Before the measurements, the protocol specified three runs of
30 sequential Agent probes and 30 system pings, requiring all replies, zero
capture drops, each Agent/capture RTT difference at most 1 ms and each
Agent/system-ping median difference at most 1 ms. No run was discarded.

| Run | Agent and ping replies | Agent median | ping median | Maximum per-packet difference |
| --- | --- | ---: | ---: | ---: |
| 1 | 30/30 each | 0.539 ms | 0.360 ms | 0.221 ms |
| 2 | 30/30 each | 0.526 ms | 0.337 ms | 0.193 ms |
| 3 | 30/30 each | 0.523 ms | 0.361 ms | 0.264 ms |

All runs met the stated checks. Across 90 Agent packets, the absolute
Agent/capture difference had median 0.145 ms and p95 0.192 ms. The test binary
SHA-256 is `c0ec12431ce70e216a3328f120826cc15d86aebdaea233f20d041a9ceafc8a13`;
its source tree matches this candidate's Agent tree apart from the test wrapper
and built binary. The retained raw evidence is on MAC-WAN under
`/tmp/nekomari-v181-physical-lan-uBba5X`. A prior setup attempt failed to
write the capture file before any probes; its record is retained separately
under `/tmp/nekomari-v181-physical-lan-Zwuftg`. Neither endpoint's settings
were changed. This is ICMP evidence for that wired LAN path, not a claim about
other LANs or TCP latency.
