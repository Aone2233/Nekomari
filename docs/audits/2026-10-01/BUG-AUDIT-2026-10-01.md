# P1 — 已确认缺陷

## P1-1【严重】9/10 节点的"流量"读数整体消失（v1.6.5 面板 × 遗留 v1.6.2 agent）

**证据（线上 + 代码 + 已部署主题，三段闭合）：**

1. 面板侧只给"计数器连续性可验证"的上报计算区间增量，判据要求 agent 提供 `CounterEpoch`：
   `internal/metricstore/interval_traffic.go:18`
   ```go
   valid := report.CounterEpoch != "" && previous.epoch == report.CounterEpoch && …
   ```
   v1.6.2 的 agent 没有该字段（`protocol/v2/jsonrpc.go:157-162` vs `v1.6.2:protocol/v2/jsonrpc.go:157`），因此永远 `valid=false`，只写入 `traffic.interval.valid = 0`，**不写 `traffic.interval.up/down`**。
2. 读取侧把 `sum` 改道到区间序列：`web/rpc/jsonrpc/public.metric.go:1034-1039`（`traffic.*` 默认 `AggSum`）→ `:1046-1056`（`AggSum` 映射为 `traffic.interval.up/down`）。
3. 已部署主题确实请求 `sum`。OC424 上 `/opt/nekomari/data/theme/SAO/dist/assets/index-BultMXTI.js`：
   ```js
   var j=`traffic.up`,M=`traffic.down`,…,Fe={[j]:`sum`,[M]:`sum`,[Ne]:`max`,[N]:`max`}
   ```
4. 线上指标库直接量测：
   ```
   traffic.interval.up   : 1 条序列（entity 646e7117… = MAC Server，v1.6.4）
   traffic.interval.down : 1 条序列（同上）
   traffic.interval.valid: 10 条序列，其中 9 条值为 0，仅 MAC Server 为 1
   ```

**症状。** 主题上 9/10 节点的"流量"曲线/配额图为空或 0；任何全队流量合计实际只统计到 MAC Server 一台。v1.6.3 时该查询走的是对累积序列取 delta，遗留节点仍有（略偏低的）真实数字，因此这是 **v1.6.4/v1.6.5 引入的可见回归**。

**线上 API 端到端复现（第二轮补做，按主题的真实请求参数，只读调用 `public:queryMetrics`）：**

```
### metric_keys=['traffic.up'], aggregation='sum'   ← 未改动的 SAO 主题就是这么问的
  HK04 (legacy v1.6.2)   max_points=60    buckets=0    non-null=0    sum=0
  HK04 (legacy v1.6.2)   max_points=500   buckets=0    non-null=0    sum=0
  MAC Server (v1.6.4)    max_points=60    buckets=48   non-null=48   sum=0.3289 GB
  MAC Server (v1.6.4)    max_points=500   buckets=224  non-null=224  sum=0.3289 GB

### 对照：同一个 metric_key 改用 aggregation='last'（周期累计本身从未丢失）
  HK04 (legacy v1.6.2)   non-null=49   last=57.65 GB
  MAC Server (v1.6.4)    non-null=49   last=0.1099 GB
```

三点结论：**① 数据在库里（`last` 读得到 57.65 GB），但主题问法拿到 0 个桶**；② 与 `max_points` 无关（60 与 500 都是 0），不是点数预算造成的假象；③ 只有 MAC Server 有数据。这就是"9/10 节点流量显示为空"的直接成因。

**顺带发现一个小接口脆弱点（低）**：若同一个请求里同时要 `traffic.up` 与 `traffic.interval.up`，`sum` 会把前者也映射到后者，于是报 `duplicate series specification for metric "traffic.interval.up"` 并**整批失败**。主题没有这么问，所以当前不触发；它同属 P1-23 那一类脆弱性（单个指标的参数问题会打掉整批查询）。

**修复方向（两条路，代价不同）：**
- **(a) 面板侧回退**：读取层在 `traffic.interval.*` 无数据时回退到 `traffic.*` + `last`（并标注质量），或在区间无效时返回逐点 `null` 而非空序列。**不需要移动 fleet**，一次发版即可。主题侧改成请求 `last` 只能算绕过，面板仍应给出正确语义。
- **(b) 升级其余 9 台 agent 到 ≥ v1.6.4**：它们就会上报 `CounterEpoch`，区间序列自然填充。已在 MAC-WAN（唯一的 v1.6.4）上实证有效——它是全队唯一 `traffic.interval.valid = 1` 的节点。代价是动 fleet，按 `docs/RELEASING.md` 的流程走；顺带也能拿到完整的 `quality` 契约（P2-4 的另一半）。

两条都需要注意：**升级 agent 不会伪造历史**——`docs/DEPLOY-OC424.md` 已声明升级前的历史区间仍是未知，因此 (a) 若作为过渡手段，(b) 才是终态。

`ubuntu` 属于 `adm` 组，可读全部 nginx 日志；该主机同时跑着 gitea、halo、vaultwarden、influxdb、couchdb 等十余个容器，任何以 ubuntu 或 adm 身份运行的进程都能拿到全队凭据。保留期 14 天，历史 `.gz` 同样含 token。

**轮换清单（逐节点比对日志中的 token 与数据库现值，精确到台）：**

| 节点 | 版本 | 是否需轮换 |
|---|---|---|
| AkkoCloud SJ / BandwagonHost MegaBox / CloudLeadInno / HK04 / JPKD2 / MAC Server / NOSLA / ShunDun DE / 并行智算云 | v1.6.2 ×8 + v1.6.4 ×1 | **是（9 台）** |
| 甲骨文 OC424（面板自身） | v1.6.2 | 否 |

即 **9/10 必须轮换**。唯一幸免的正是面板自己那台——它的 agent 走 `--endpoint http://127.0.0.1:25774` 直连容器，不经过 nginx，所以它的 token 从未进入访问日志。这反过来精确印证了泄露机制：**凡走公网入口的节点，token 必然落进 nginx 日志**。

同一条 URL 还会同时进入：

- **各节点自身 journal**（已实测，MAC-WAN：`Failed to POST v2 pull …?token=…: EOF`）——报障时随手贴日志即泄露；
- **Cloudflare 侧**（请求来自 CF 边缘 IP `172.71.x.x`，TLS 在 CF 终止，查询串对 CF 可见）；
- 任何中间代理/网关的日志。

**还有一个让取证变难的点：nginx 访问日志里记的是 Cloudflare 边缘 IP，不是真实访客。** 实测该端点最近的来源 IP 全是 CF 段（`104.22.20.94`、`172.69.134.37`、`172.71.100.161`…）；`/etc/nginx` 下没有 `set_real_ip_from`。仓库的 `deploy/nginx-nekomari.conf:67-81` 只为**应用**设置了经过 CF 段校验的 `X-Real-IP`（面板自己的 `logs` 表里确实存的是真实 IP，例如登录事件的 `192.220.32.17`），但访问日志仍是默认 combined 格式。**后果：如果有人用泄露的 token 冒充节点上报，从 nginx 日志上无法归因。**

**这直接抵消了 D1 的凭据加固。** D1 把 token 从 `ExecStart` 移到 0600 文件（已实测 MAC-WAN：`--token-file …/.agent-credentials`，`ps` 中已无 token），但同一个 token 换了个更容易被记录的位置出现。凭据泄露 = 完整冒充该节点上报任意数据、领取任意任务、参与文件传输。

**修复方向。** 改为 `Authorization: Bearer <token>` 头（WebSocket 用握手头或首帧认证）；同时把 nginx `log_format` 中的查询串脱敏，并轮换全部 10 个 token（它们已经泄露，轮换是必要动作）。

**一个必须先知道的前提（第七轮核实）：** 服务端对 `Authorization: Bearer` 头的支持**只在 `/api/rpc2`**（`web/rpc/jsonrpc/transport.go:215-219`）。agent 实际用的 `/api/clients/v2/rpc` 走 `web/api/principal.go:33` → `web/api/Auth.go:168` 的 `extractClientToken`，**只认 `?token=` 与 `?Authorization=` 两个查询参数和请求体 token，完全不读 HTTP 头**（`principal.go:20-21` 读 `Authorization` 头是给 API Key 用的，另一套凭据）。所以这条修复**必须两侧都改**，只改 agent 只会把泄露换个参数名——`?Authorization=` 一样进日志。`web/api/package` 里的改动很小（照 `transport.go:218-219` 补一个 header 分支），但少了它这个修复就是无效的。详见 [FIX-PLAN](./FIX-PLAN-2026-10-01.md) 的 F1b。

## P1-3【高】面板"最近 24 小时流量"被放大约 270–287 倍（跨月归零时可达 3 万倍）

**证据。** `frontend/src/pages/admin/dashboard.tsx:487-488` 对 `traffic.up/down` 请求 `last`，随后 `:281`、`:302-303` 把每个桶的 `last` **累加**，`:1060-1061` 渲染在"最近 24 小时流量"下（`:1020`）。而 `traffic.*` 是**计费周期累计**（`internal/metricstore/report_mapping.go:38-39` 存的是 `CycleUp/CycleDown`），对一个持续增长的累积量按桶求和没有物理意义。24 小时窗口下桶数 ≈288（默认 `max_points=500`，`CeilStandardInterval` 到 5 分钟）。

线上 API 直接复现（第二轮，完全照 `dashboard.tsx` 的算法：`aggregation=last` 后把每个桶的值累加）：


## P1-16【低】`pkg/jsruntime` 的 `-race` 测试失败（数据竞争）—— ✅ 已修复

```
$ go test -race -count=1 ./pkg/jsruntime/
WARNING: DATA RACE  ×3
--- FAIL: TestHTTPClientRequestErrorWithoutListenerStillCloses (0.11s)
    testing.go:1865: race detected during execution of test
FAIL	github.com/Aone2233/nekomari/pkg/jsruntime	5.952s
```

**竞争的两侧（修之前完整读了一遍报告）：**
- 写：`console.(*Module).write` → `fmt.Fprintln(m.output, …)`（`console.go:112`），由 **JS 事件循环的后台协程**经 `Report` 触发（定时器回调失败时）；
- 读：测试协程里的 `bytes.Buffer.String()`（`node_test.go:292`）。

**修的时候发现它其实是两个问题，不是"测试写得不好"一个：**
1. **模块侧**：`Module` 把调用方给的 `io.Writer` 当成可以随便并发的——可它自己会从两个方向写（调用 `Call` 的协程 + 事件循环协程）。两个写者同时写一个**不保证并发安全**的 writer，本身就会互相破坏。已加 `writeMu sync.Mutex` 串行化模块自己的写入。

```
$ go test -race -count=1 <本轮及此前改动过的 12 个包>  → 全部 ok
```

1. `web/rpc/jsonrpc/public.metric.go:231-233`：只要请求里某个 `traffic.*` 指标带了 `rate`/`delta`，就 `return nil, InvalidParams`，**整个响应失败**而不是该指标为空：
   ```go
   if _, cumulative := trafficCumulativeMetrics[metricKey]; cumulative && (algorithm == metric.AggRate || algorithm == metric.AggDelta) {
       return nil, rpc.MakeError(rpc.InvalidParams, "rate/delta on billing-cycle counters is not continuity-safe; …", nil)
   }
   ```
   而 v1.6.3 的服务端恰好把客户端的 `sum` 映射成 `AggDelta`——任何沿用/缓存了那个聚合名的客户端，升级到 v1.6.4+ 后会整页图表全空，而不是只少一条曲线。
2. 线上实测：同一请求里同时要 `traffic.up` 与 `traffic.interval.up`，因为 `sum` 会把前者也映射到后者，直接报
   `duplicate series specification for metric "traffic.interval.up"`，同样是整批失败。
   ```
   {"code": -32602, "message": "Failed to query metrics: metric: invalid argument: duplicate series specification for metric \"traffic.interval.up\""}
   ```

**影响。** 未改动的 SAO 主题不触发（它只问 `traffic.up`），属**面向未来的脆弱性**：一个指标的一个参数问题会表现为"整个面板图表都空了"，排查成本远高于"某条曲线没数据"。

**修复方向。** 逐指标降级（该指标返回 null/错误标记），而不是让整批失败；或在请求校验阶段就把冲突/非法聚合归一化掉。

## P3-4【中】`Presence.Coverage` 是"首个数据到末个数据之间的密度"，不是"窗口覆盖率"——已线上复现

## P3-6【中】`CrossesAt` 的 `time.Duration` 溢出，空闲节点被判成"本周期会超限"

# P5 — 采集数值定义（第四轮补审）

> 这一轮我先怀疑"内存数值算错了"，**核实后推翻了自己的假设**——数值是正确的、验收是严的，只剩一个命名问题。过程留在下面，因为"先验证再定性"正是这份报告的要求。

## P5-1【低】`ram_mode: "htoplike"` 这个名字与实际公式不符，会让人以为面板算错

**先澄清：不是正确性缺陷。** 该口径在 `docs/MONITORING-ACCURACY-FIXES-2026-09-30.md:88` 被明确声明为**独立定义**（"正常内存口径为 Total-Available；include-cache 为 Total-Free；htoplike 为独立定义"），且被验收脚本以 **< 1%** 的容差钉死。

**实测（MAC-WAN，同一时刻）：**
```
主机 free -m:            Mem total 7853   used 1359   free 485   buff/cache 6312   available 6493
主机 MemTotal-MemAvailable = 1353.5 MiB
面板上报                    = 1039–1063 MiB（15 分钟内 14 个样本，稳定）
agent/monitoring/unit/mem.go:119-139 的公式:
        Used = MemTotal − MemFree − Cached − SReclaimable − Buffers + Shmem
             = 8042028 − 503324 − 4600908 − 1098900 − 764220 + 1192 = 1075868 kB = 1050.7 MiB ✓ 与面板吻合
```
即面板显示的是**旧版 `free` 的 "used"**（不含 buff/cache）。而 `htop` 与现代 `free` 显示的是 `Total − Available`（1359 MiB）。两者在本机相差 **29%**。

**问题在哪。** 名字叫 `htoplike`，但它**不是 htop 的数**。用户拿面板和 `htop`/`free` 对照时，会看到约 29% 的差，合理的结论是"面板算错了"或"这台机器内存比看上去更紧张"——而方向上恰恰相反：面板显示的是**更低**的已用量（看起来更宽裕）。定义本身站得住（匿名页 + 不可回收部分），缺的是**把定义暴露出来**：`ram_mode` 只存在于给程序看的 `quality` 里，UI 不显示。

**建议（纯文案，零风险；但【不要】改线缆上的值）：** 不要改 `ram_mode` 的字符串——它是**对外契约**：验收脚本 `canary-panel.py:169` 断言 `ram_mode == "htoplike"`，已写入历史 `quality` 的数据也带着它，改名等于破坏 API 与历史可比性。正确做法是在**管理页的内存卡片上加一条口径提示**（如"已用 = 总内存 − 空闲 − 可回收缓存，与 htop/`free` 的 used 口径不同，通常更低"）。**更不建议改公式**——那会让历史序列与验收基准同时失效，收益不抵代价。

**顺带一个正向确认（值得写下来）：** 验收脚本 `docs/audits/2026-09-30/canary-kernel.py:42-43` 对本口径的参考实现是
```python
"ram_htoplike_used": mem["MemTotal"] - mem["MemFree"] - mem["Buffers"] - mem["Cached"] - mem["SReclaimable"] + mem["Shmem"]
```
与 agent 的公式**逐项一致**，并在 `canary-panel.py:229` 上断言 `max(ram_errors) < 0.01`——所以"MAC-WAN 的内存验收通过"是一个**容差 1% 的真实结论**，不是走过场。（我最初的怀疑来自只看到被折行的 grep 输出；读原文件后已推翻。）

# P6 — 备份与迁移（第五轮补审，此前未覆盖）

先说清楚这一片**做对了什么**（这几条是真实保证，不是客套）：`backupOnVersionUpgrade` 的顺序约束都有注释说明且被测试钉住（`TestUpgradeBackupSnapshotPrecedesMigrations`、`…SkippedWhenVersionUnchanged`、`…SkippedOnFreshInstall`、`…SkippedWithoutVersionID`）——打包必须在 `migrations.Run` **之前**（否则归档里是升级后的状态、回滚不了本次升级）、在 `.zip` 恢复逻辑之后、在 WAL checkpoint 之后、在 `config.SetDb` 之前（否则旧版宽 `configs` 表会被 AutoMigrate 加 PRIMARY KEY 而 panic）。备份失败**不阻止启动但不写版本标记**，于是下次启动会重试——这个取舍是对的。

## P6-1【中】失败的备份会留下一个**截断的 zip**，它和正常备份无法区分；而一个损坏的最新备份会让保留策略**永久停摆**

**证据 1 —— 失败路径不清理半成品：** `database/dbcore/dbcore.go:26-92`
```go
out, err := os.Create(dstZip)     // 先建文件
…
zw := zip.NewWriter(out)
defer zw.Close()
walkErr := filepath.Walk(absSrc, func(path string, info os.FileInfo, err error) error {
    …
    fh, err := os.Open(path); if err != nil { return err }          // 任一文件读失败
    if _, err := io.Copy(w, fh); err != nil { fh.Close(); return err } // 或磁盘写满
    …
})
if walkErr != nil { return walkErr }   // ← 直接返回，dstZip 留在磁盘上
```
`backupOnVersionUpgrade`（`:294-297`）拿到错误后只打日志、返回 false，**不删除这个文件、也不校验产物**。它的文件名与正常备份完全一致（`upgrade-<ts>.zip`），只是内容不全。

**证据 2 —— 保留脚本会对损坏的最新备份"罢工"：** `/usr/local/bin/prune-upgrade-backups.sh`（`set -euo pipefail`）
```bash
for f in "${files[@]:0:$KEEP}"; do          # 只检查要保留的那几个
  if command -v python3 >/dev/null 2>&1; then
    python3 - "$f" <<'PY'
bad = zipfile.ZipFile(sys.argv[1]).testzip()
if bad: raise SystemExit("corrupt entry: %s" % bad)
PY
  fi
  echo "  keep    $(basename "$f")"
done
for f in "${files[@]:$KEEP}"; do rm -f "$f"; done   # 删除循环没有任何检查
```
`python3` 非零退出在 `set -e` 下会**直接终止整个脚本**（它不在 `if` 条件里，而在 `if` 体里），于是：打印到一半 → 退出 → **一个文件都没删**。而截断的 zip 打不开（中央目录在尾部），必然触发。脚本既不修也不删这个文件。

**合并后果（完整失效链）：** 某次升级备份失败 → 留下一个截断 zip → 它是最新的 → 每周的 prune 检测到损坏 → 整个 prune 中止 → 从此**不再删除任何备份**，目录无上限增长（当前 11 个 / 452 MB，见 P4-1 的频率错配）。与此同时，任何"取最新那个 upgrade-*.zip 回滚"的人/脚本会拿到一个坏档，**而这个事实只在真正需要回滚时才暴露**。

**建议。** ① 打包写成临时名、成功后再 `rename`（同 P2-2 里 agent 自更新的正确做法）；失败时删除半成品。② prune 把"损坏的幸存者"改成**跳过并告警**而不是致命错误（`|| true` + 明确日志），并考虑把坏档移入 `*.corrupt` 便于取证。③ 备份完成后做一次 `testzip()` 自检。

## P6-2【低-中】自动升级备份按设计**排除 metrics.db**，所以指标库不在这条回滚路径的保护范围内

`upgradeArchiveExclusions`（`dbcore.go:225-234`）显式排除 `metrics.db`、`metrics.db-wal`、`metrics.db-shm`，注释说明是"把本地指标库留在原地"。线上核实：最新自动备份 `upgrade-20260930-122444.zip` 中 `metrics.db` 出现 **0 次**（2717 个文件、解压 69 MB）。

后果：v1.6.4 的迁移是**会把遗留监控历史搬进指标库**的（`internal/migrations/legacy_monitoring.go`），而这条自动化回滚路径恰恰不保护指标库——如果迁移损坏了 `metrics.db`，`upgrade-*.zip` 帮不上忙。当前靠的是运维**手工做的停机全量备份**（`/opt/nekomari/backups/*`，我已在 P4-1 验证它含两个库且完好）。

这属于"设计取舍 + 依赖人工"的组合：代码注释里写明了取舍，但没有任何地方在升级前提示"指标库不在此次自动备份内"。**建议**在升级日志/文档里明确这一步，或对指标库单独做一次轻量快照。

## P6-3【低-中 · 未证实】遗留迁移没有可恢复的进度标记：中途崩溃会从头重跑

`internal/migrations/legacy_monitoring.go`（631 行）是流式批处理（`legacyMonitoringBatchSize = 500`，`:23`），但**过程中不删除源行**——删除只发生在 `CompleteLegacyMonitoringMigration`（`:178-195`），它先 `dropLegacyMonitoringTables`、**最后**才写标记（注释说明这是刻意的："Keeping the marker last prevents a failed finalization from being reported as a completed migration"）。

因此：迁移进行到一半时进程崩溃 → 标记未写、源表仍在 → 下次启动**从头重跑整个迁移**（`:50` 的 `LegacyMonitoringProgress` 只是给 UI 的回调，不落库，没有任何断点记录）。

**未证实的一点（已被后续审计解答，见 P7 一节的"无问题"清单）：** 我原先担心重复写入会按 count 重复计数。**第六轮的结论是：不会。** 写入路径是"按 `(metric, entity, tags, bucket)` 在一个事务里 upsert"（`pkg/metric/rollup_import.go:76-95`），同一次调用内出现重复 bucket 会**显式报错**（`:60-62`）；迁移自身的测试就是**跑两遍导入并断言仍是同一个 bucket 值**（`legacy_monitoring_test.go:80-107`）。所以中途崩溃后重跑是安全的，"从头重跑"只意味着白做功，不会污染数据。

**本部署不受影响**：生产上该迁移已干净完成（`migration_legacy_monitoring_to_metric_store_done = true`，遗留表 `client_infos`/`records`/`gpu_records`/`ping_records`/`monitoring_histories` 均已不存在）。这条是**面向未来同类迁移**的建议：加一个按表或按游标的断点记录，让重跑可续。

# P7 — 数据安全与 GeoIP（第六轮补审）

## P7-1【中 · 潜伏】当某指标的保留期短于该层级的跨度时，**整层 rollup 会被无条件删除**

**机制（已逐行确认）** `pkg/metric/store.go:1288-1308`：
```go

```
`:1332-1333` 用 `key.all` 执行删除——即**删掉该层级的所有行，不看年龄**。

**为什么本部署不会中招（线上反证，决定性）：**
- 迁移路径 `internal/metricstore/store.go:66-70` 用**遗留数据的跨度**作为新定义的保留期；而 `definitions.go:104-113` 的规则是"**已存在的定义保留自己的保留期**"。所以迁移建出来的定义拿到的是长保留期，之后普通启动的 1 天默认值**不会**把它们改回去。
- 线上实测：27 个定义里 **25 个是 `retention_days = 90`**，只有 `backup.age_seconds`/`backup.ok` 是 1。
- 线上实测：`ping.loss` 有 **2026-07-11 → 2026-10-01** 的 67 015 行；这些行所在的序列 tags 是 **`{"task_id":"7"}`** 这种"只有 task_id"的形状——正是 `legacy_monitoring.go` 的迁移产出（升级后的新序列带 `protocol`/`family`）。即**迁移进来的遗留历史至今仍在**，而 `metrics:retention` 每小时跑一次、已经跑过很多次。

**所以子代理的常量没读错、机制没写错，错在前提：** 它假定迁移时定义已是 1 天。`defaultRetentionDays = defaultBuiltinMetricRetentionDays = 1`（`definitions.go:11,62`）确实是最短默认，但**危险的是那两条"定义已存在且为 1 天"的路径**：metrics DSN 打不开时走的恢复流程（`RecoverStore` → 普通 `openStore` 用 1 天建定义），或先跑结构升级再进遗留导入。

**建议（低成本、纯防御）：** 让迁移在导入前检查目标 store 里各定义的有效保留期；若某定义短于遗留跨度，**要么先抬高它、要么把导入的点只写进有效策略覆盖到的层级**，并在导入报告里显式说明被丢弃了哪些层级。当前是靠"迁移自己设了长保留期"这一巧合成立的，值得从"巧合"变成"保证"。

（附带一条真实的小瑕疵：`WrittenPoints` 在 `legacy_monitoring.go:503+509` 返回的是过滤前的 `len(points)`，而 `pkg/metric/store.go:937-939` 会把 retention=0 的点静默丢掉，所以导入成功的报告数字偏大。）

## P7-2【高】启动恢复路径：安全快照失败**不阻止**删除，解压失败被忽略，归档仍被删掉

配合 `web/backup/restore.go:187-213` 的 `ValidateArchive` 只检查后缀/4 GiB/10 万条目/是否存在 `komari-backup-markup`——**从不打开 `komari.db`、不校验 SQLite 魔数、不跑 `quick_check`**。

**后果链：** 安全快照失败（某个文件不可读、ENOSPC）→ 仍然清空 `./data` → 若上传的归档不完整（例如**不是**面板自己导出的、缺 `metrics.db`），旧数据里那些文件就永久消失 → 解压失败也无所谓 → **服务端那份上传归档被删除** → `doInitialize` 继续，`dbFileExistedAtStartup=false`，gorm 建出空库，面板回到安装向导。操作员只看到几行 error 日志。

**注：** 测试里**完全没有**覆盖 `doInitialize` 的恢复分支（`pre-restore` 在所有测试中都不出现），所以这条路径从未被验证过。

# P8 — token 轮换的实操记录与由此暴露的三个问题

> 这一节记录**执行 F1a 时真实发生的一次生产事故**（由我造成、已修复、已完全恢复），以及它暴露出的三个此前没有被静态审计发现的问题。**如实记录，不粉饰。**

## P8-0 事故经过（MAC-WAN 中断约 13 分钟）

1. 我为首台金丝雀（MAC Server）生成新令牌、写入其凭据文件，然后重启 agent。此时面板 DB 里还是旧值 → MAC-WAN 开始 401 掉线。
2. 我用 `python3 - <<'PY' … PY` 去更新面板 DB，并试图把令牌经 **stdin** 传进去。**这是错的**：`python3 -` 的脚本本身就来自 stdin（heredoc），所以脚本里的 `sys.stdin.read()` 读到的是 EOF → **令牌被写成了空串**。
3. 另一处错误：我复用的本地 ssh 辅助脚本**不接受管道输入**，所以其中一次尝试根本没执行（PowerShell 报参数绑定失败）。
4. 更关键的发现：我多次用外部 `sqlite3` **在面板运行期间**写这个库。反复写之后，`clients` 表出现索引损坏：
   ```
   PRAGMA integrity_check  →  row 6 missing from index sqlite_autoindex_clients_2
   ```
   而令牌查询正是 `db.Where("token = ?", token).First(&client)`——**走的就是这个索引**。索引缺条目 ⇒ 查不到行 ⇒ 即使 DB 里明明有那个令牌，面板也返回 **401**。这解释了当时最反常的现象："面板拒绝它自己数据库里的令牌"。
   **注意 `PRAGMA quick_check` 全程返回 `ok`**——只有完整的 `integrity_check` 抓到了它。
5. 修复：备份当前库 → `docker stop` → `REINDEX` → `integrity_check` 恢复 `ok` → `docker start`；随后在**容器停止**状态下写入令牌（确定性），再启动、重启 agent。
6. 最终状态：**10/10 节点上报**（全队采样年龄同为 97.4s，即 1 分钟桶边界）、`komari.db` 与 `metrics.db` 的 `integrity_check` 均为 `ok`、容器 `healthy/0 重启`、10 分钟内 0 条错误日志。修复前的库已备份到 `/opt/nekomari/backups/before-reindex-20261001T071031Z`。

## P8-1【中 · 能力缺口】面板没有"轮换 client token"的管理接口，逼着运维去直接写库

全仓库的 client token 操作只有：创建节点时生成（`clients.CreateClient`）、读取（`admin:getClientToken`）。**没有任何"重新生成/设置 token"的接口。** 想轮换只能绕过面板直接写 SQLite——而这正是上面第 4 步的事故来源（在面板运行期间外部写库不可靠，且会留下索引不一致）。

**建议**：加一个 `admin:rotateClientToken`（返回新 token），由面板自己的连接写入并顺带 `REINDEX`/校验。这把"只能做且危险"变成"有受支持的做法"。这也是本报告里唯一一条**因为我要执行修复才发现**的缺口。

## P8-2【中】认证依赖索引，而索引不一致时**静默**变成 401；`quick_check` 抓不到

- 现象：面板一切"看起来正常"（健康检查通过、日志无错、其他 9 台正常），但被损坏索引影响的那一行**永远认证失败**。
- 为什么难查：`GetClientUUIDByToken` 是 `First(&client)`，索引缺条目时 SQLite 不报错，只是"查不到"——与"令牌不对"完全同形。
- 为什么没被现有手段发现：**`PRAGMA quick_check` 返回 `ok`**（它不校验索引与表的一致性），只有 `PRAGMA integrity_check` 才报 `row N missing from index …`。

**建议**：① 启动时对主库跑一次 `integrity_check`（大库可只在版本升级后跑），发现不一致就在日志里**显式告警**而不是等某个节点莫名 401；② 把"索引缺失"这类问题纳入运维巡检（一条 `sqlite3 … 'pragma integrity_check;'` 即可）。

## P8-3【低 · 运维】轮换的正确顺序与两个易踩点

已验证可用的顺序（每台约 10–20 秒面板停机）：
```
1) docker stop nekomari                     # 必须在面板停止时写库，否则外部写不可靠
2) 在节点侧写入新凭据文件（0600）
3) 直接改 clients.token（此时没有并发写者）
4) 校验：integrity_check = ok、无空令牌、该行 token 长度正确
5) docker start nekomari
6) 重启该节点的 agent —— 否则它会停在 "Max retries reached → POST fallback" 的退避状态，
   即使令牌已经正确也要等很久才会自己恢复（实测：重启 agent 后 2 秒内 "WebSocket connected"）
```
另：**不要把令牌经 stdin 传给 `python3 -` 的 heredoc 脚本**（脚本自身占用 stdin），改用临时文件（`umask 077`）读取，用完即删。
