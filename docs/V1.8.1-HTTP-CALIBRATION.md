# HTTP phase injected-delay comparison, 2026-11-15

On a Linux x86-64 test host with Go 1.26.9, the candidate Agent's
`httpProbeWithResolver` ran against an isolated loopback HTTP server. A test
resolver and the server independently timed their own injected delays. For
each of 0, 50 and 200 ms, three consecutive runs were retained, with a
predeclared per-phase absolute error limit of `max(5 ms, 2% of reference)`.
All 18 comparisons met the limit. The opt-in test is
`agent/server/http_field_calibration_test.go`; it also passed with the Go
race detector in a separate run.

| Phase | Delay (ms) | Absolute error median (ms) | Absolute error p95 (ms) |
| --- | ---: | ---: | ---: |
| DNS | 0 | 0.000 | 0.000 |
| DNS | 50 | 0.001 | 0.014 |
| DNS | 200 | 0.002 | 0.002 |
| TTFB | 0 | 0.066 | 0.341 |
| TTFB | 50 | 0.395 | 0.698 |
| TTFB | 200 | 0.299 | 0.412 |

The p95 uses the nearest-rank method, so with only three samples it is the
largest observed error, not a reliable population percentile. The resolver
timing brackets the injected delay within the same process; it is not a
separate DNS server or system-resolver measurement. Server timing brackets
the delay before writing headers, so TTFB also contains loopback transport,
scheduling and HTTP handling overhead. This is a plain-HTTP, single-hop
function-level check, not a full Agent-to-Panel report or a calibration of
TCP, TLS, redirect chains or other operating systems. Detailed output is
retained locally under `/tmp/nekomari-v181-http-field.log`, not committed.

## Local DNS server comparison

On the same date and host, a separate opt-in test
`agent/server/http_dns_field_calibration_test.go` used a real local UDP DNS
server and Go's resolver with a custom dialer, without changing system DNS.
For 0, 50 and 200 ms separately timed server delays, all three consecutive
samples at each delay met the same predeclared tolerance with the race
detector enabled. The probe's DNS phase includes resolver and loopback
transport overhead in addition to the reference server delay.

| Delay (ms) | Absolute error median (ms) | Absolute error p95 (ms) |
| ---: | ---: | ---: |
| 0 | 1.004 | 1.879 |
| 50 | 0.522 | 0.613 |
| 200 | 0.701 | 0.741 |

Nearest-rank p95 is again the maximum of only three runs. The server answered
one A query; this is not a calibration of the machine's configured resolver,
AAAA/dual-stack lookup, packet loss, external DNS or redirects. The detailed
output is retained locally in `/tmp/nekomari-v181-http-dns-field.log`.

## TLS handshake comparison and initial failed reference

An initial TLS experiment used only the independently timed server-injected
delay as the expected duration. With the race detector, two of nine samples
exceeded the 5 ms tolerance: the first zero-delay handshake was 63.249 ms
above its delay and one 200 ms sample was 5.172 ms above its delay. That
experiment **failed**, and its output is retained in
`/tmp/nekomari-v181-http-tls-field.log`. Its reference excluded certificate
loading, cryptography and other handshake work, so the excess alone cannot
establish that the Agent's handshake timing was wrong.

A subsequent, separately defined comparison timed the server's full TLS
handshake around `tls.Server.Handshake`, with separately recorded server
delays of 0, 50 and 200 ms. It used a temporary, locally trusted certificate,
with verification enabled in a child process, and the candidate Agent probe.
All three runs per delay met `max(5 ms, 2% of reference)` under `-race`:

| Injected delay (ms) | Absolute client/server interval difference median (ms) | p95 (ms) |
| ---: | ---: | ---: |
| 0 | 0.031 | 0.053 |
| 50 | 0.020 | 0.180 |
| 200 | 0.004 | 0.052 |

Nearest-rank p95 is the maximum of three. The first zero-delay client and
server intervals were both about 57 ms, supporting the interpretation that
the first experiment omitted real handshake cost; the two experiments are
not identical and do not prove the cause of every outlier. The retained
opt-in test is `agent/server/http_tls_field_calibration_test.go`; detailed
output is `/tmp/nekomari-v181-http-tls-handshake.log`. Server and client
interval boundaries are close but not identical, on the same loopback host;
this does not cover external TLS, redirects or production certificates.

## TCP loopback packet comparison

On the same Linux x86-64 host, the opt-in
`agent/server/http_tcp_field_calibration_test.go` used the production HTTP
probe and a local HTTP listener. A separate raw packet socket observed SYN
and the client's final ACK; the server's accepted client port and a fresh
listener per run bind the capture to the actual request. Three consecutive
runs under `-race` compared that interval with the Agent's TCP phase against
the predeclared HTTP-phase 5 ms absolute minimum tolerance. All three met it:

| Run | Agent TCP (ms) | SYN-to-ACK reference (ms) | Difference (ms) |
| ---: | ---: | ---: | ---: |
| 1 | 0.350 | 0.074 | 0.276 |
| 2 | 0.167 | 0.055 | 0.112 |
| 3 | 0.107 | 0.011 | 0.096 |

The median difference was 0.112 ms and nearest-rank p95 was 0.276 ms, the
maximum of three. Packet timestamps are taken when the capture process reads
packets, not kernel hardware timestamps, and the packet interval does not
include the complete client syscall overhead. This is a near-zero-delay
loopback comparison rather than a delayed or physical-network calibration.
The raw socket requires `CAP_NET_RAW`; output is retained locally in
`/tmp/nekomari-v181-http-tcp-bound-field.log`. An earlier three-run capture
did not bind captured ports to the request and could consume a previous
connection's packets; its output remains at
`/tmp/nekomari-v181-http-tcp-field.log` but is not valid calibration evidence.

## Single redirect comparison

An opt-in `agent/server/http_redirect_field_calibration_test.go` test on the
same Linux host injected a separately timed 25 ms resolver delay on each of
two hostname hops, an 80 ms first response and a 40 ms final response.
Three consecutive runs under `-race` met `max(5 ms, 2% of reference)` for
both the summed DNS phase and final-hop TTFB; total time retained the first
hop delay and the reported redirect count was one.

| Phase | Absolute error median (ms) | p95 (ms) |
| --- | ---: | ---: |
| Sum of two DNS delays | 0.017 | 0.022 |
| Final-hop TTFB | 0.588 | 0.704 |

Nearest-rank p95 is the maximum of three. This is one HTTP-to-HTTP redirect
using an injected resolver and loopback server, not external DNS, HTTPS,
longer chains or an Agent-to-Panel check. Detailed output is retained in
`/tmp/nekomari-v181-http-redirect-field.log`.

## HTTPS-to-HTTPS redirect comparison

On the same host, `agent/server/http_https_redirect_field_calibration_test.go`
used two loopback HTTPS listeners and a temporary trusted certificate. Each
listener independently timed its complete handshake and response delay. The
first hop injected 70 ms in the handshake and 80 ms before redirecting; the
final hop injected 20 ms and 40 ms. Three consecutive runs under `-race` met
the predeclared `max(5 ms, 2% of reference)` limit for final TLS and TTFB.
The result had one redirect, status 200 and a verified leaf expiry; total
time also retained the first-hop handshake and response delays.

| Phase | Absolute difference median (ms) | p95 (ms) |
| --- | ---: | ---: |
| Final TLS handshake | 0.098 | 0.150 |
| Final TTFB | 0.522 | 1.021 |

The p95 is the maximum of three samples. This compares neighboring client and
server timing boundaries on one host, not an external network or end-to-end
Agent report. It does not establish behavior for longer chains, HTTPS-to-HTTP
redirects, failed handshakes or production certificates. Detailed output is
retained locally at `/tmp/nekomari-v181-https-redirect-field.log`.

## Final-hop TLS failure and plain-HTTP redirect

A local untrusted-certificate test on 2026-11-15 exposed that the Agent's
handshake completion callback recorded elapsed time even when verification
failed. The candidate now reports TLS duration only for a successful final
connection. A separate test in a child process trusts only the first TLS hop:
redirects from it to plain HTTP and to an untrusted TLS endpoint both omit
the final TLS duration. The plain final hop remains reachable; the failed TLS
hop is not reachable. These tests use actual loopback servers and passed with
the race detector. They do not change historical samples or establish the
behavior of every network or redirect error.

An additional Linux network-namespace test built the candidate Agent with the
race detector and ran its actual executable against a disposable Panel using
the ordinary scheduler and authenticated WebSocket. A local HTTPS server
with an untrusted certificate produced a stored TCP-phase point and
`http.reachable=0`, with no `http.tls_ms` point. The existing executable DNS
unknown/SLA control also passed after sharing this fixture. The opt-in test is
`TestOrdinaryAgentExecutableTLSFailureMetric` in
`web/api/client/ordinary_agent_executable_e2e_test.go`. It exercises one
single-attempt failure and does not prove production rollout, all redirect
paths or historical data cleanup.

## Informational response followed by timeout

On 2026-11-15 a loopback server sent `103 Early Hints` and then withheld the
final response. The previous candidate returned a TTFB point even though the
request timed out, because Go's first-byte trace fires for the informational
response. The candidate now omits TTFB unless a final response exists. When a
final response does follow, the existing first-byte meaning still includes an
earlier 1xx on that final hop; it is not redefined as time to final headers.
Both cases passed three race-enabled repetitions. The actual Agent executable,
ordinary scheduler, authenticated WebSocket and metric store also passed the
isolated timeout case: `http.reachable=1`, TCP present, TTFB absent. This is
one HTTP/1 loopback scenario; historical points and other protocols are not
rewritten or independently covered by it.

## HTTP deadline while DNS is pending

An isolated slow custom DNS control showed that the HTTP client could return
its deadline before the transport's resolver completed. The previous candidate
left that error unclassified, allowing the Panel to treat it as loss even
though no target connection was attempted. The Agent now reports
`dns_failure` when the deadline arrives during a pending hostname lookup,
including a lookup after a redirect. The DNS duration is omitted in that case.
Race-enabled tests cover the initial lookup and redirect with a blocked
resolver. A real race-built Agent with an unresponsive disposable DNS server,
ordinary scheduler, authenticated WebSocket and metric store produced an
unknown point and no ping loss, latency, HTTP DNS/TCP/reachability points or
SLA outage in two repetitions. The test is opt-in as
`TestOrdinaryAgentExecutableHTTPDNSDeadline`. It does not rewrite past data or
cover every possible timeout boundary.
