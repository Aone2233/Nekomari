# Mixed Agent address preference check, 2026-11-15

A disposable Panel fixture scheduled the same ordinary TCP task to actual
v1.7.30 and candidate Agent executables over authenticated WebSockets and
queried the resulting successful latency points in its metric store. An
isolated Linux network and mount namespace provided dual-stack loopback TCP
listeners and a temporary hosts file, with IPv6 listed before IPv4. Both
Agents used Go's resolver. The task requested IPv4 preference.

The v1.7.30 Agent selected IPv6, the first resolved address; the candidate
Agent selected IPv4. The stored points carried those respective family tags.
Two consecutive runs of the retained opt-in fixture with the Panel test under
`-race` passed after an earlier successful run. No production configuration,
service or host network was changed.

The legacy binary was built from tag `v1.7.30`, commit
`1a77f04074fb197cbc54e348b9dab87bdf79a16e`, SHA-256
`76c307a5f126bf0bd11265c3c4ff64d969628fd3c8e38207bebd8d518e266943`.
The candidate binary was built from commit
`779066fd69711d7f2ffed957e1240f5f70f00df0`, SHA-256
`b7c6030a8d547e8e48e0cec4128606ee16799553e3b758b8f0b003cb655283c1`.
The binaries were ordinary builds; the race detector covered the Panel test,
not the Agent processes. To repeat, build trusted old and candidate binaries
and supply their absolute paths as `NEKOMARI_MIXED_OLD` and
`NEKOMARI_MIXED_NEW`, set `NEKOMARI_MIXED_EXEC_E2E=1`, and run
`go test -race ./web/api/client -run '^TestMixedExecutablePreference$'` on a
Linux host with network and mount namespace privileges. The namespace bind
mount is private and disappears with the child process.

This shows one mixed-version IPv4-preference case with a deterministic hosts
file; it does not test actual external DNS ordering, every Agent version,
IPv6 preference, fallback or a production fleet rollout. Older Agents may
ignore the preference, so mixed-version results need not use the same path.

## Configured DNS follow-up

Ordinary ICMP, TCP and HTTP probes previously used `net.LookupHost` even
when an Agent's custom DNS setting was present, while pinned probes used the
configured resolver. A local control with a disposable DNS server confirmed
that the ordinary lookup bypassed it. The candidate now shares the existing
Agent resolver: absent a custom setting it returns the system resolver, while
a configured resolver follows its existing DNS fallback behavior. This is an
intentional change in probe destination after upgrading a configured Agent;
old Agents retain the old behavior. Literal IP addresses bypass lookup.

The race-enabled `TestOrdinaryProbeUsesConfiguredDNS` runs a disposable UDP
DNS server with A and AAAA answers, checks both address preferences and a
literal, then makes real HTTP and TCP probes to a local listener using the
configured resolver. Three repetitions passed. This covers local probe
functions and DNS queries, not an Agent executable, DNS failure/fallback
scenarios, other resolver configurations or a production rollout. It is not
a timing calibration of the configured resolver.

The opt-in `TestMixedExecutableCustomDNS` additionally ran actual v1.7.30 and
candidate `b23d79e` Agent executables through the ordinary scheduler,
authenticated WebSockets and metric store in isolated Linux network and mount
namespaces. Its system DNS returned only IPv6 for the fixture name, while the
configured custom DNS returned only IPv4; both listeners were local. With no
task family preference, stored success points were IPv6 for the old Agent and
IPv4 for the candidate, and the custom DNS received the fixture query. Two
race-enabled Panel test repetitions passed; the Agent binaries themselves were
not race builds. The candidate binary SHA-256 was
`9eb0b17371ea057424d0cb37b6084f09aef7631672dc33348159bebb1810e5ac`;
the old binary hash is given above. Run with the same environment variables as
the preceding mixed-Agent test and `-run '^TestMixedExecutableCustomDNS$'`.
The isolated fixture binds UDP port 53 and mounts its own resolver and hosts
files inside the private namespace. It does not touch the host resolver.

Initial experimental runs stalled because the DNS fixture did not answer
unrelated startup queries; the fixture now returns NXDOMAIN for them. A later
control with the name in the hosts file used that file before custom DNS, as
Go's resolver permits. The final test removes the name from hosts and supplies
both DNS answers separately. The passing result does not establish behavior
for DNS failures, fallback servers, every probe protocol, or a production
fleet.
