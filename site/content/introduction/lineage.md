# 与上游 Komari 的关系

Nekomari 是 [Komari](https://github.com/komari-monitor/komari) 的分支。上游仓库已于 2026-09 归档，本分支继续维护。

| | |
|---|---|
| 上游项目 | komari-monitor/komari |
| 上游状态 | **已归档**（最后推送 2026-09-14） |
| 基线版本 | `1.5.0-fix1`（commit `0ca87aa`） |
| 上游最后一个正式版 | `1.5.1` |
| 本分支起点 | `1.6.0` |
| 许可证 | MIT（上游版权 Copyright (c) 2025 Komari Moniter，依 MIT 保留） |

上游把项目拆在多个仓库里（服务端、Web 前端、探针）。本分支整合为**单一仓库**，`frontend/` 与 `agent/` 直接内置。

## 保留了哪些上游命名

这些名字是**接口契约**，改名会破坏整个生态，所以刻意保留：

- `komari-plugin.json` / `komari-theme.json` —— 每个已有插件与主题都用这两个文件名
- 插件市场的 `komari` 字段与 `CheckKomariVersion` —— 插件市场的线格式
- `komari-agent-<os>-<arch>` 发布产物名 —— 探针自更新按这个名字找资产
- `X-Komari-Transfer-*` / `X-Komari-Upload-*` HTTP 头 —— 探针与面板之间的文件传输

而 Go module 路径已全部改为 `github.com/Aone2233/nekomari`，没有残留指向上游的 import。

## 版本号为什么从 `0.1.x` 改成了 `1.6.0`

这个改动值得单独说明，因为它是**功能性的**，不是记账。

插件市场对每个插件都有版本门槛（`komari` 字段，例如 `>=1.6.0`），**面板和服务端两端都强制**。本分支早期用 `0.1.x` 编号 —— 一条与血缘无关的新序列 —— 于是服务端被判为比**每一个**插件都旧：官方市场 19 个插件里有 15 个装不上，**七个通知插件全部**要求 `>=1.6.0`。

所以从 `1.6.0` 起，版本号**接续上游编号**：

| | |
|---|---|
| 上游基线 | `1.5.0-fix1` |
| 上游最后一个正式版 | `1.5.1` |
| 上游的下一个条目 | `1.6.0-pre1`（预发布，从未转正） |
| **本分支从此开始** | **`1.6.0`、`1.6.1`、……** |

需要说清的是：这**不是**"上游存在 1.6.0 可供对比"的意思（并不存在）。它是继承来的插件生态**识别本服务端能不能跑**的机制，而这个方向上是诚实的 —— 本分支的功能集确实超过上游 `1.5.1`。

版本号还必须是**纯 `X.Y.Z`**。两端的解析都是按 `.` 切分后逐段转整数，而它们对带后缀的版本**失败方式相反**：面板解析不了就认定"任何约束都不满足"，把每个插件都标记为不兼容；服务端则**故意忽略**解析不了的运行版本（"malformed server version must not block plugin loading"）而放行。**一个界面说不可能，服务端说没问题。**

### 残留风险

要求 `>=1.6.0` 的插件可能用到上游在 `1.6.0-pre1` 里新增、而本分支基线没有的 API。这种插件会通过版本门槛，但在加载时失败。版本门槛是**版本比较**，不是**能力检查** —— 要变成能力检查就得逐个读插件源码。发现时的正确修法是提高那个插件在索引里的要求、或补上缺失 API，**而不是降低本分支的版本号**。
